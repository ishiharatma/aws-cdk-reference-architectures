# RDS のマルチ AZ とリードレプリカの比較 - AWS CDK リファレンスアーキテクチャ

[![🇯🇵 日本語](https://img.shields.io/badge/%F0%9F%87%AF%F0%9F%87%B5-日本語-white)](./README.ja.md)
[![🇺🇸 English](https://img.shields.io/badge/%F0%9F%87%BA%F0%9F%87%B8-English-white)](./README.md)

![Level 200](https://img.shields.io/badge/Level-200-yellow?style=flat-square)

Amazon RDS で最も混同されやすい2つを、1つのデータベースで並べて比べます。**マルチ AZ** のプライマリは、同期レプリケーションのスタンバイを **可用性** のために持ち、スタンバイは読み取れません。**リードレプリカ** は、非同期で、読み取れて、フェイルオーバーには参加せず、**昇格** させて独立したデータベースにできます。VPC 内のプローブ Lambda が両方に接続し、確認スクリプトが、主張ではなく実測で違いを示します。各エンドポイントが受け付けるもの、レプリカがどれだけ遅れているか、フェイルオーバーがそれぞれに何をするか、昇格が実際には何を意味するかです。[`fis-arch-i-rds-multiaz`](../fis-arch-i-rds-multiaz/)(インスタンスとクラスターの比較)の、マルチ AZ の比較を補う内容です。

| | マルチ AZ のスタンバイ | リードレプリカ |
|---|---|---|
| 目的 | 可用性: 自動フェイルオーバー | 読み取りのスケールと、手動の災害対策の選択肢 |
| レプリケーション | 同期 | 非同期 |
| 読み取り | できない(エンドポイントがない) | できる |
| 障害時の引き継ぎ | する(自動) | しない。手動で昇格が必要 |
| 昇格後 | 該当なし | 別のデータベースになり、元を追わなくなる |

## 🏗️ アーキテクチャ概要

![Architecture Diagram](overview.drawio.svg)

### 主要コンポーネント

- **VPC**: 2つのアベイラビリティゾーン、分離サブネットのみ、NAT ゲートウェイなし。プローブは、インターフェイスエンドポイント経由で Secrets Manager に到達します。
- **プライマリ**: RDS for PostgreSQL 17 のマルチ AZ DB インスタンス(`db.t4g.micro`)。暗号化済みで、自動バックアップを有効にしています(リードレプリカに必要です)。
- **リードレプリカ**: プライマリのシングルインスタンスのリードレプリカ。暗号化済みで、同じサブネットにあります。読み取り用なので、マルチ AZ にはしません。
- **プローブ Lambda**(Node.js 24、ARM64、VPC 内): アクションは `info`、`write`、`lag`、`watch`、`diverge`、`heartbeat`。データベースに到達できるのは、セキュリティグループによりプローブだけです。
- **ハートビートのルール**: 1分に1回の小さな書き込み(設計判断5を参照)。
- **ReplicaLag アラーム**: レプリカの `ReplicaLag` に対する CloudWatch アラーム。
- **`test-comparison.sh`**: 比較を行い、マルチ AZ のフェイルオーバー、そして昇格を実行します。

## 🎯 設計判断とベストプラクティス

### 1. マルチ AZ のスタンバイは、使えるレプリカではない

マルチ AZ インスタンスのスタンバイは見えません。エンドポイントも接続もなく、読めるものがありません。同期したコピーを持つので、障害が起きても失うのは数秒で、データは失いません。2つ目のコピーから読みたいなら、それはリードレプリカです。「性能のためのマルチ AZ」と書かれた設計の多くは、実はレプリカが欲しいものです。

### 2. レプリカは非同期で、速いがゼロではない

プローブは、プライマリにマーカーを書き、レプリカで読めるようになるまでの時間を測ります。30回の書き込みで、中央値7 ms、p95 20 ms、最大21 ms でした(先の実行では最大385 ms)。これは、健全でアイドルなレプリカの値です。書き込み負荷が高いとき、リージョンをまたぐときは大きくなり、レプリカは「自分が書いたものを読める」ことを約束できません。書いた直後に読む必要があるものは、プライマリから読みます。

### 3. レプリカは書き込みを拒否する

レプリカへの書き込みは `cannot execute CREATE TABLE in a read-only transaction` で失敗します(`pg_is_in_recovery()` はレプリカで `true`、プライマリで `false`)。読み取り専用のトラフィックはレプリカのエンドポイントへ、それ以外はプライマリへ向けます。

### 4. フェイルオーバーがそれぞれに何をするか

プライマリを強制的にフェイルオーバーさせ(`reboot-db-instance --force-failover`)、両方のエンドポイントに毎秒新しい接続を開いた結果です。

| エンドポイント | フェイルオーバー中 |
|---|---|
| プライマリ | 1回の停止で13秒間到達できず、その後に復帰。インスタンスは `ap-northeast-1a` から `ap-northeast-1c` に移った(スタンバイが引き継いだ) |
| レプリカ | 影響なし。プローブ330回中330回が成功 |

フェイルオーバーの後、レプリカは自分で新しいプライマリに再接続しました。新しい書き込み20件がすべて見えるようになり、中央値は5 ms でした。レプリカはフェイルオーバーには参加しませんが、フェイルオーバーを乗り越えます。書き込みが回復するまでの間も、レプリカからの読み取りは動き続けます。

### 5. `ReplicaLag` は書き込みがないと嘘をつく

PostgreSQL では、`ReplicaLag` メトリクスは「最後に再生したトランザクションからの経過時間」です。**アイドル** のプライマリでは、何も遅れていなくても1分あたり60秒ずつ増えます(最初の実行では91、151、211、271秒と増え、書き込みが来ると16秒に戻りました)。そこでこのスタックは、1分に1回ハートビートの行を書きます。これでメトリクスは0から約60秒の範囲に収まります(観測は21〜51秒)。上のマーカーの遅延はミリ秒ですが、メトリクスはそうなります。結果として2つのことが言えます。アラームのしきい値がハートビートの間隔以下だと、健全なレプリカで発報するので、既定値は120秒にしています。もっと厳しいアラームにするには、しきい値より短い間隔でハートビートを書く必要があります。

### 6. 昇格は、戻れない扉

レプリカを昇格させると、書き込める普通のデータベースになります。昇格の15秒後にプライマリへ書いた内容は届かず、インスタンスはもう元のソースを示しません。昇格は、災害対策か移行のための道具です。最後に複製されたトランザクションより後にプライマリへ書かれたデータは失われ、アプリケーションの向き先は自分で切り替える必要があり、レプリカの関係は永久になくなります(元に戻すには新しいレプリカを作ります)。マルチ AZ のフェイルオーバーには、どれも要りません。

### 7. 両方を、別々の理由で使う

| 必要なこと | 使うもの |
|---|---|
| データを失わず、操作もせずに、インスタンスや AZ の障害を乗り切る | マルチ AZ |
| 読み取り(レポート、検索、ダッシュボード)を逃がす | リードレプリカ |
| 両方 | ここにあるような、1つ以上のレプリカを持つマルチ AZ のプライマリ |
| リージョンの喪失から復旧する | 昇格できるクロスリージョンのレプリカ、または別リージョンへコピーしたバックアップ |
| より速いフェイルオーバーと、読めるスタンバイ | マルチ AZ DB クラスター(`fis-arch-i-rds-multiaz` を参照)か Aurora |

### 8. レプリカはあえてシングルインスタンス

マルチ AZ のレプリカも作れますが、これは読み取り用です。可用性はプライマリの役目で、レプリカが落ちたら、読み取りをプライマリに戻すか、新しいレプリカを作ります。

### 9. 環境別パラメータ

`parameters/<env>-params.ts` で、VPC、インスタンスクラス、割り当てストレージ、ReplicaLag アラームのしきい値を設定します。

## 🏛️ Well-Architected との対応

| 柱 | この構成での対応 |
|---|---|
| 運用上の優秀性 | `test-comparison.sh` が振る舞いを主張ではなく実測する、遅延のアラーム、CloudFormation 管理 |
| セキュリティ | 分離サブネット、プローブだけを許可するセキュリティグループ、暗号化したインスタンスとシークレット、パブリックアクセスなし |
| 信頼性 | 自動フェイルオーバーのためのマルチ AZ のプライマリ、フェイルオーバーを乗り越えてレプリケーションを再開するレプリカ |
| パフォーマンス効率 | 読み取りをレプリカに移せる。複製の遅延をミリ秒で実測 |
| コスト最適化 | レプリカは1インスタンス分、マルチ AZ は2つ目の分。NAT ゲートウェイなし(下記) |
| 持続可能性 | 最小のインスタンスクラス、待機する NAT ゲートウェイなし |

## 💰 コスト最適化

`ap-northeast-1` の概算です(料金ページで確認してください)。

| 項目 | 目安 |
|---|---|
| マルチ AZ のプライマリ(`db.t4g.micro`) | 1時間あたり単一インスタンスの約2倍 + ストレージ |
| リードレプリカ(`db.t4g.micro`) | 1時間あたり単一インスタンスの約1倍 + ストレージ |
| Secrets Manager のインターフェイスエンドポイント(2 AZ) | 1時間あたり約0.03 USD |
| ハートビートの Lambda | 1日1,440回の短い実行。月に数セント |

データベースは1時間あたりおよそ0.1 USD です。検証一式(デプロイに約27分、確認に約25分)は1 USD をはるかに下回りました。終わったらスタックを削除してください。レプリカは、読み取る人がいてもいなくても、コピー元と同じ費用がかかります。

## 🔒 セキュリティ上の考慮事項

### 実装済み

- データベースは、インターネットへの経路がない分離サブネットに置き、`publiclyAccessible: false` にしています。
- データベースのセキュリティグループは、プローブのセキュリティグループからの PostgreSQL だけを許可します。プローブが到達できるのは、データベースと Secrets Manager のエンドポイントだけです。
- 両方のインスタンスでストレージを暗号化し、マスターパスワードは生成したシークレットです。
- 開発環境以外では、削除保護とスナップショットを有効にします。

### CDK Nag の抑制(理由付き)

| ルール | 理由 |
|---|---|
| AwsSolutions-IAM4 / IAM5 | Lambda の VPC アクセス用ポリシーは AWS マネージドで、リソースレベルの指定がない |
| AwsSolutions-RDS2 / RDS3 | 暗号化は有効。レプリカは設計上シングル AZ |
| AwsSolutions-RDS6 | リファレンスを小さく保つため、プローブは IAM データベース認証ではなく生成したシークレットを使う |
| AwsSolutions-RDS10 | 削除保護は開発環境以外で有効 |
| AwsSolutions-RDS11 | プローブだけが到達できるネットワークで、既定のポートを使う |
| AwsSolutions-SMG4 | 短時間の比較用。ローテーションは `secrets-rotation-aurora` で扱う |
| AwsSolutions-L1、VPC7、CdkNagValidationFailure | 作成時点の最新の Node.js、記録すべきインターネット経路がない、ルールが評価できない CIDR の参照 |

### スコープ外(環境ごとに追加)

クロスリージョンのレプリカ、独自のパラメータグループと Performance Insights を持つレプリカ、RDS Proxy、IAM データベース認証、クライアントでの証明書の検証(プローブはあえて省略しています)。

## 🧪 動作確認スクリプト

`./test-comparison.sh --project <project> --env <env> [--no-promote]` は次を行います。

1. プライマリがマルチ AZ で、別の AZ にスタンバイがあること。レプリカがプライマリのシングル AZ のリードレプリカであること
2. `pg_is_in_recovery()` が、プライマリで false、レプリカで true であること
3. プライマリは書き込みを受け付け、レプリカは拒否すること
4. プライマリに書いた30個のマーカーがすべてレプリカに現れること。中央値、p95、最大値を報告します
5. ハートビートが動いている間、CloudWatch の `ReplicaLag` が有界であり、アラームが `ALARM` でないこと
6. 両方のエンドポイントに毎秒接続しながらのプライマリの強制フェイルオーバー。プライマリの停止の時間、AZ の変更、レプリカの可用性、レプリケーションの再開
7. レプリカの昇格。もうソースがなく、書き込め、その後のプライマリへの書き込みが届かないこと

2026-10-10 に `ap-northeast-1` で検証し、すべて成功しました。昇格は元に戻せないので、レプリカを残したいときは `--no-promote` を使い、その後はスタックを削除してください。

## 🔧 トラブルシューティング

### `ReplicaLag` が1分あたり60秒ずつ増える

プライマリがアイドルです。PostgreSQL には再生するものがないので、メトリクスは最後のトランザクションからの経過時間を測ります。定期的に書き込む(このスタックのハートビート)か、このメトリクスだけでなくマーカーの書き込みで遅延を判断してください。

### 健全なレプリカでも ReplicaLag のアラームが発報する

しきい値がハートビートの間隔以下です。60秒より大きくするか、ハートビートをもっと頻繁に書いてください。

### レプリカを作れない

ソースには、自動バックアップ(`backupRetention` が1日以上)と、PostgreSQL では同じメジャーバージョンのエンジンが必要です。

### レプリカへの書き込みが失敗する

それが正しい動作です。リードレプリカは読み取り専用です。書き込みはプライマリのエンドポイントへ送ってください。

### 昇格の後にスタックの削除が失敗する

昇格したレプリカは普通のインスタンスなので、スタックはそれを削除できます。削除保護が有効な場合(本番)は、先に無効にしてください。
